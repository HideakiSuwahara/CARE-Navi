# レビューループ

1回のループは「実装 → レビュー（並列） → 修正 → テスト → 記録」。1日に最低1回、画面を足したら必ず回す。機能凍結（11/6 正午）以降はループだけを回す。

## 手順

1. **記録ファイルを作る**
   `node scripts/new-review.mjs --scope "今回見る範囲（例: ボードと割当）"` を実行し、できた `docs/reviews/YYYY-MM-DD-loopN.md` のパスを控える。

2. **現状を固める**
   `npm run lint && npm run typecheck && npm test && npm run check:wording` を通す。通らないならレビューの前に直す（壊れたものをレビューしない）。

3. **レビューを並列に出す**（Agent ツールで同時に起動。各エージェントには「見る範囲」「起動方法（`npm run dev` のURL）」「記録ファイルのパス」を渡す）
   - `product-guardian`: 範囲・表現・出所
   - `care-domain-reviewer`: 現場の妥当性
   - `ux-first-timer`: 3ペルソナで初見操作（Playwright で動かす）
   - `a11y-reviewer`: 色・大きさ・キーボード・印刷
   レビュー担当にはファイルを書き換えさせない。指摘と修正案だけを受け取る。

4. **指摘を1つの表にまとめる**
   記録ファイルの「指摘」表に、重大度・箇所・指摘・修正案を転記する。重複は1行にまとめ、矛盾する指摘は原則（CLAUDE.md）に照らして採否を書く。「対応しない」にも理由を書く。

5. **修正する**（`frontend-builder` に渡すか、自分で直す）
   高 → 中 → 低の順。表現の規則違反は重大度に関わらず先に直す。1つの指摘につき1コミットが望ましい。

6. **テストを通す**
   `npm run lint && npm run typecheck && npm test && npm run check:wording`。E2E があれば `npm run e2e`。結果を記録ファイルの「テスト結果」に書く。

7. **受け入れ条件を更新する**
   直した項目が docs/acceptance.md のどれに当たるかを確認し、チェックを更新する（`acceptance-check` スキル）。

8. **記録して締める**
   記録ファイルの「対応」列を埋め、持ち越しを書き、コミットする。コミットメッセージは `review: loopN — 修正 n 件、持ち越し m 件`。

## ループの判定

- 高の指摘が 0 で、3ペルソナのシナリオが全員「完走」なら、そのスコープは合格。
- 2ループ続けて同じ指摘が出たら、直し方ではなく設計（docs/screens.md）を疑い、決定記録を書く。

## やらないこと

- レビュー担当にコードを書かせない。
- 指摘を黙って捨てない。「対応しない」は理由つきで残す。
- ループの途中で範囲を広げない（新機能は次のループの「スコープ」に回す）。
