# 決定記録

決めたことは、決めた理由と一緒に残す。あとから読む人（審査員・次の開発者・自分）が「なぜこうなっているか」を実装から推測しなくて済むようにする。

## ファイル

- 置き場所: `docs/decisions/NNNN-短いスラッグ.md`（NNNN は 4 桁連番。既存の最大 + 1）
- 既存の記録を書き換えない。覆すときは新しい番号で書き、古い方の冒頭に「NNNN で置き換え」と 1 行足す。

## 書式

```markdown
# 決定記録 NNNN: （決めたことを一文で）

日付: YYYY-MM-DD
状態: 採用 ／ 置き換え済み（→ MMMM）
置き換える決定: （あれば番号と該当箇所）

## 決定
（何をどうするか。実装・画面・文言に落ちる粒度で、箇条書き 3〜8 行）

## 理由（お客さん優先の順）
1. 今日のリーダーにとって
2. 応援・職員にとって
3. 施設長・委員会にとって
4. 開発・工程にとって
（審査員の観点は最後。理由にならないなら書かない）

## 失うもの・置き換え
| 失うもの | 置き換え | 評価 |

## 影響する場所
- docs/screens.md §…、src/…、docs/acceptance.md #…

## 見直す条件
（この決定を再検討するきっかけ。例: 試用で n 人中 m 人が迷ったら）
```

## 手順

1. 既存の `docs/decisions/` を読み、矛盾しないか、置き換えになるかを確かめる。
2. 上の書式で書く。固有名詞（個人名・他プロジェクト名）は書かない。設計思想は本プロジェクトのものとして書く。
3. 影響する文書（docs/screens.md、docs/acceptance.md、CLAUDE.md）を同じコミットで直す。
4. コミットメッセージは `decision: NNNN 短い説明`。

## 判断の原則（CLAUDE.md と同じ。迷ったらここに戻る）

- お客さんの順番: 今日のリーダー → 応援・職員 → 施設長・委員会 → 審査員。
- 初週にリーダーが使うものだけを必須に。
- 変更は 10 秒以内、フロアのスマホで。
- 数字は業務に付ける。人には付けない。
- 製品内で AI を使わない。判断は人。
- 言わないことは言わない。
