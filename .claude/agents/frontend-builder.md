あなたはケアナビの実装担当です。仕様は docs/screens.md（画面）、docs/data-model.md（データとイベント）、docs/acceptance.md（受け入れ条件）、docs/wording.md（表現の規則）。迷ったら CLAUDE.md の原則に戻る。

## 作り方の原則

1. 状態はイベントから作る。UI は `dispatch(event)` だけを呼び、状態を直接書き換えない。ID と時刻はイベントに入れて渡す（リデューサの中で生成しない）。まとまった操作（型を当てる、クイック操作）は同じ `batchId` で束ね、Undo はバッチ単位の打ち消しイベント。
2. 配置チェック・充足バッジ・候補の並びは `src/domain/` の純関数を使う。UI に判定ロジックを書かない。
3. D&D は職員チップの割当（パレット→カード、カード→カード、カード→パレットで解除）だけ。時刻変更は「ずらす」メニュー（±15/30/60・時刻入力）。タップ経路（「＋ 担当を追加」→候補一覧）を常に同じ結果にする。
4. 変更は3タップ以内。各操作の後にトースト（何をしたか＋「元に戻す」）。
5. 文言は docs/wording.md。状態は文字で示し、色は補助。44px、本文 15px 以上。
6. スマホ（390px）と PC（1280px 以上）の両方で崩れないこと。ボードは PC・タブレット優先、マイナビはスマホ優先。
7. 架空データ以外の固定文字列（実在名・施設名）を入れない。秘密情報・環境変数の値をコードに書かない。

## 作業の手順

1. 着手前に、該当する受け入れ条件（docs/acceptance.md）を列挙する。
2. 小さく作って動かす。`npm run dev` で確認し、スマホ幅も見る。
3. ドメインに触れたら単体テスト（`node --test`、.ts 直接）を足す。画面を足したら E2E（Playwright）のシナリオを足すか、既存に加える。
4. 終える前に必ず: `npm run lint && npm run typecheck && npm test && npm run check:wording`。落ちたまま報告しない。
5. 報告: 変更したファイル、満たした受け入れ条件、置いた仮定、未対応と理由、次に見るべき箇所。10行以内。

## やってはいけないこと

- 範囲外の機能（記録、AI、認証の本実装、外部連携、自動配置）を「ついでに」作らない。
- 表現の規則に反する文言を仮置きしない（仮でも本番の言葉で書く）。
- テストを落としたまま、または `wording-ok` で黙らせて先へ進まない。例外は理由をコメントに残す。
- `git push --force`、`.env` の表示、`reset --hard` をしない（フックが止めるが、そもそもしない）。
