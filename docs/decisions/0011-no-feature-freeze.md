# 決定記録 0011: 機能凍結をやめ、提出まで磨き続ける

日付: 2026-11-05
状態: 採用
置き換える決定: 0001 判断の原則 9「11/6（金）正午に機能凍結。以降は修正・レビュー・動画のみ」と、0001 の「必須（11/6 金 正午までに揃える＝機能凍結）」の締切の意味。0002・0005・0009・0010 の中で凍結に触れている箇所も、この記録で読み替える。

## 決定
- 11/6（金）正午の機能凍結はしない。提出（目標 11/8（日）18:00、期限 20:00）まで、機能の追加・改修を続けてよい。
- その代わり `main` はいつでも提出できる状態に保つ。コミットのたびに `npm run lint && npm run typecheck && npm test && npm run check:wording` を通し、本番デプロイが壊れていないことを確かめる。
- 画面や操作を足したら、その日のうちにレビューループを回す（`review-loop`）。これは今までどおり。
- 範囲（作るもの／作らないもの）と表現の規則は変えない。新しい機能を足すときは、これまでどおり決定記録で判断を残す。
- 磨く目当ては「実際の施設の人が、自分の施設のデータで使って手応えを感じること」。サンプル施設だけで動くものにしない。自分の施設で始めてから毎朝使えるまでの道筋（職員・利用者・日課・番・業務表）を優先する。
- 動画はほぼできているので撮り直しは前提にしない。動画に映る場面の見た目を大きく変えたときだけ、その場面を撮り直す。

## 理由（お客さん優先の順）
1. 今日のリーダーにとって: 日課の追加・職員の直し方など、自分の施設で使い始めるのに足りないところが残っている。凍結すると、それを提出版で埋められない。
2. 応援・職員にとって: 初見でつまずくところを、試用の結果を見てから直せる。
3. 施設長・委員会にとって: 自分の施設のデータで試せる範囲が広がる。
4. 開発・工程にとって: 凍結の目的（提出版を壊さない・レビューと動画の時間を残す）は、「main をいつでも提出できる状態に保つ」と「画面を足したらその日にレビュー」で守る。

## 失うもの・置き換え
| 失うもの | 置き換え | 評価 |
|---|---|---|
| 凍結後に修正だけを回す、落ち着いた期間 | コミットごとの 4 つのチェックと CI、画面を足した日のレビューループ | 壊れたまま提出する危険は残る。直前の大きな変更は控えめにする |
| 動画と製品の見た目がそろっている | 映る場面を大きく変えたときだけ撮り直す | 動画と細部がずれることはある |
| 受け入れ確認を凍結の後に一度で済ませる | 提出前にもう一度 `acceptance-check` を回す | 確認の回数が増える |
