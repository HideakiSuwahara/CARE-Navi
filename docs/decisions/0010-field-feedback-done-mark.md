# 0010 現場の聞き取りを受けた改修（一日の流れの一覧・「終わった」の印・終わっていない枠の確認）

- 日付: 2026-11-04
- 状態: 決定。決定 2・3・5 と前提の文を 2026-11-04 に実装（下記「実装して決めたこと」）。決定 4（対象の方ごとの印・進み具合）はハッカソン後
- 置き換える決定: 0001 Q10「簡易実施記録は今回作らない。型（CareRecord）は設計だけ残し、ハッカソン後に判断する」→ 判断した: **作る**。0001 Q1 の前提「多くの施設には毎朝ホワイトボードに書く分担がある」→ 前提を改める（下記）。README「作らないもの」の「実施の記録」「通知」→ 書き換える。wording.md 原則 2「記録しないものを断定しない」→ 「時刻が過ぎただけで断定しない」は残し、人が付けた印は示す
- 関連: 0001（判断の原則 4「朝は人に役割を付けるだけ」は変えない）、0004 §4（対象の方ごとのサポートの 1 行）、0006（困ったら）、0007（全体: 時刻を過ぎた業務は薄く「（時刻を過ぎました）」。完了とは言わない）

## 聞き取り（2026-11-04）

介護現場の方 1 名から聞いた（ユニット型の施設の話が中心。従来型特養についても意見あり）。本人の了解を得た引用ではないので要約だけを書く。名前・施設名は書かない。動画・提出文で「現場の声」として引用しない（wording 原則 7）。

1. 誰がどの業務をやるかは、基本的には振り分けない。ユニットごとに、業務全体の流れを一覧で見られるのが非常に良い。
2. ユニット型は 1 ユニットの職員が 3 人ほどと少ない。「誰がやるか」より、「この時間に何をするか」「誰（利用者）にどんな注意事項が必要か」が分かることがありがたい。
3. 担当業務が分かる方が動きやすいので、担当の仕組みは「あった方が良い」。
4. 業務が行われたか行われなかったかを押せるものがあると良い。誰が終わらせたかは要らない。終わった／終わっていないを 1 タップで。
5. 終わっていない業務がリーダーに知らされ、リーダーが確認する流れがあると良い。
6. 他のユニットへの応援、新人、スポットワーカー（介護経験のある方）が来たとき、何をどうするかが分かるのは非常に便利。
7. 従来型特養は人数が多いので、さらに助かりそう。おむつ交換などは一斉に行うため、誰が終わって誰が終わっていないかを一覧を見るだけで判断できると、さらに良い。
8. 朝に業務を人へ振る場面は無い。あるとすれば、誰かが休みになって勤務調整をするとき。

## 決定

1. **前提を改める。** 困りごとは「毎朝の分担の手書き」ではなく、「一日の流れが慣れた人の頭の中にあり、初めての人（応援・新人・スポット）に見えない」こと。朝の「この内容で作る」は、人に業務を振る操作ではなく、番で決まった一日を一枚の時間割として出す操作として説明する。人に業務を付け直すのは、誰かが休んだ日の組み直しと日中の変更だけ（今の設計のまま）。concept.md §2・README・動画の説明をこれに合わせる（動画は v5 で変更済み）。
2. **「終わった」の印を作る。** 本当に使える道具にするため（本人 2026-11-04）。枠（業務カード）ごとに、担当の人かリーダーが 1 タップで付け外しできる。元に戻すで戻る。**誰が付けたかは画面に出さない**（履歴には残す。「犯人探しに見せない」）。時刻が過ぎただけでは付かない。
3. **終わっていない枠をリーダーが確認できる。** 終了時刻を過ぎて印の無い枠を、リーダーのスマホ「全体」とボードの見出しで数え、時間順に見られる。リーダーはそこから「終わった」を付けるか、「ずらす」「中止」「担当を追加」で扱う。
4. **一覧は新しい画面を作らず、ボードで見る。** 従来型の一斉の業務（おむつ交換 20人 など）は、対象の方ごとに印を付けられ、枠に進み具合（12/20）が出る。
5. **利用者ごとの注意事項を手元画面の上段に寄せる。** 0004 §4 の「対象の方ごとに時刻とサポートが必要なことの 1 行」を、業務詳細で対象の方の一覧と一緒に上の方へ。内容は施設が業務表に書く（記録ソフトからの転記はしない）。
6. **担当（番で付く仕組み）はそのまま残す。**

## 実装の案（実装するセッションで確かめて決める）

- 語: 「完了」「済」「実施」「未実施」「完了率」は使わない（wording §2 はそのまま）。印の語の候補は「終わった」（押す前は「終わったら押す」）。印の無い枠に「まだ」とも書かない。進み具合は「12/20」の数字だけ。率は出さない。
- データ: イベント種別を足す（枠の印の付け外し、対象の方ごとの印の付け外し）。リデューサで枠の `done`／対象の方ごとの `doneResidentIds` を組み立てる。履歴には誰が付けたかを残し、画面には出さない。
- 0007 との整合: 印のある枠は「終わった」の印＋薄く。印が無く時刻を過ぎた枠は、0007 のとおり「（時刻を過ぎました）」のまま通常の濃さで、「終わっていない n 件」に数える（「担当未定 n件」には数えない）。
- ボード: 終わった枠はチェック印＋薄く。「過ぎたが印なし」は通常の濃さで区別する（今の「過ぎた予定は薄く」と見分けが要る）。見出しに「終わっていない n 件」（担当未定の件数と並べる）。
- 手元画面: 「いまの時間の予定」「きょうの流れ」の各行に 1 タップの印。業務詳細の対象の方の一覧は、方ごとに印を付けられる。
- リーダーのスマホ「全体」: 「終わっていない n 件」の絞り込み。プッシュ通知は作らない（通知の基盤を持たない。画面を開いたときに見える形）。
- README: 「作らないもの」の「実施の記録」を「介護記録（内容の記録）、CSV・一覧・率」に書き換え、「終わった印は持つ」を「何ができるか」に足す。wording.md 原則 2 と §2 の「完了／済／終了」の行を、「時刻が過ぎただけで『終わった』にしない。人が付けた印だけを示す」に書き換える。
- 受け入れ条件（docs/acceptance.md）と E2E を足す: 印を付ける／外す／元に戻す、対象の方ごとの印と進み具合、「終わっていない n 件」の数え方。
- 機能凍結（11/6 正午）との関係: 決定 2（枠の印）と決定 3（見出しの件数）を先に。対象の方ごとの印（決定 4）と薄さの区別は、間に合わなければハッカソン後。

## 理由（お客さん優先の順）

1. 今日のリーダーにとって: 「振る」場面は無く、「回っているか」を見る場面が毎日ある。印が無いと、ボードは日中、予定表のままで価値が薄い。
2. 応援・職員にとって: 一斉の業務で、自分の分がどこまで済んだか、残りはどこかが見える。
3. 施設長・委員会にとって: 変わらない。数字は業務に付ける。印の数で人を評価しない。率は出さない。
4. 審査員にとって: 実在の現場の聞き取りで前提を改め、製品に反映した記録になる。

## 実装して決めたこと（2026-11-04）

- **語**: 押す前「終わったら押す」（スマホの行は幅が狭いので「終わった」）、押したあと「✓ 終わった」。`aria-pressed` で状態を伝える。見出しは「終わっていない n件」。「完了」「済」「未実施」「まだ」は使わない。wording.md 原則 2 と §2 を書き換えた。
- **データ**: `TaskInstance.done?: boolean`、イベント `task.done { id, done }`（`src/domain/events.ts`）。打ち消しは変更前の値の `task.done`。誰が付けたかは `actorId` に残り、画面には出さない。`setDoneEvents`（`src/domain/commands.ts`）は 1 イベント 1 バッチなので、元に戻すは 1 タップ。
- **数え方**: `unfinishedTasks(state, date, now)`（`src/domain/checks.ts`）＝ 終わりの時刻 ≤ いま、印なし、休憩と中止を除く。「担当未定」とは別に数える（両方に当たる枠は両方に数える）。`AllRow.done / unfinished`、`unfinishedCount`（`src/domain/leader.ts`）。
- **どこに置いたか**:
  - 自分の予定: 「きょうの流れ」の各行の右（44px）、「いまの時間の予定」のカードの下。押すと画面下に一言と「元に戻す」（`DoneToast`）。
  - 業務詳細: 見出しの下（一緒に の次）。「対象の方」は「お願いすること」の直後へ移した（決定 5）。
  - 全体（リーダー）: 見出しに「終わっていない n件」（押すと最初の該当行へ）。時刻を過ぎた行と印の付いた行には行に「終わった」、これからの行は「⋯ → 終わったにする」。
  - ボード: ツールバーに「終わっていない n件 →」（担当未定と並ぶ。押すと該当カードへ順に移動）。カードは ✓ と薄い文字（`data-done`）。時刻を過ぎて印の無いカードは通常の濃さ（`data-unfinished`）。詳細パネルの操作の列に「終わったら押す」。
- **薄さの区別**（0007 を改めた）: 薄くするのは「終わった」の印がある行・カードと「中止」だけ。時刻が過ぎただけの行は通常の濃さのまま「（時刻を過ぎました）」。受け入れ条件 L45 を書き換えた。
- **通知は作らない**: 件数は画面を開いたときに見える（見出し）。プッシュ通知の基盤は持たない。
- **決定 4（対象の方ごとの印、12/20 の進み具合）**: 間に合わないので作っていない。入れるときは `doneResidentIds` を同じ要領で足す（data-model.md §9）。
- **テスト**: 単体 `src/domain/__tests__/done.test.ts`（付ける・外す・元に戻す、時刻だけでは付かない、休憩・中止を数えない）。E2E `e2e/done.spec.ts`（ボード）、`e2e/done.phone.spec.ts`（自分の予定・業務詳細・全体）。
